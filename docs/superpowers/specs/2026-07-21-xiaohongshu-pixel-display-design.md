# TC002 小红书粉丝数像素显示设计

## 目标

将小红书粉丝数 Bridge 当前生成的 52×16 PNG 改为参考图风格：黑色背景，左侧为红色小红书像素图标，右侧为醒目的白色粉丝数。参考图右侧的四个灰白状态点不属于实现范围。

## 范围

- 只修改 `apps/mqtt/xiaohongshu-follower-counter` 的 PNG 渲染与相关测试。
- MQTT broker 发现、设备绑定、topic、Chrome 扩展和 payload 外层结构保持不变。
- 继续发布到每台设备现有的 `custom/display` topic。
- 不显示用户昵称、装饰下划线或状态点。

## 52×16 布局

- 画布：52×16 RGB，背景纯黑 `#000000`。
- 图标区域：左侧 14×14，起点 `(0, 1)`，主体使用小红书红 `#FF2442`，内部为白色像素标识。
- 间距：图标与数字之间至少保留 2 个黑色像素列。
- 数字区域：从 `x=16` 开始到 `x=51`，白色 `#FFFFFF`，在可用区域内水平居中并在 16 像素高度内垂直居中。

## 粉丝数字规则

1. 将输入转换为非负整数。
2. 1–3 位数字使用两倍缩放的 5×7 像素数字，突出显示。
3. 4–6 位数字使用一倍缩放的 5×7 像素数字，保留完整数值。
4. 7 位及以上使用紧凑缩写：优先显示一位小数的 `K` 或 `M`，整数部分达到三位时去掉小数。
5. 缩写仍需经过可用宽度测量，选择能完整放入数字区域的最大缩放倍数。
6. 不截断数字，不允许绘制越过 52×16 边界。

示例：

- `18`：大号 `18`
- `123`：大号 `123`
- `1234`：小号完整 `1234`
- `123456`：小号完整 `123456`
- `1234567`：紧凑显示 `1.2M`

## 渲染结构

`renderFollowerPng(snapshot)` 继续创建 RGB 像素缓冲区，并依次完成：

1. 绘制小红书图标；
2. 格式化粉丝数；
3. 根据文本宽度选择缩放倍数；
4. 在右侧区域居中绘制；
5. 通过现有 `encodeRgbPng` 编码为 52×16 PNG。

`buildCustomAppPayload` 保持当前兼容结构：

```json
{
  "duration": 31536000,
  "text": [],
  "image": [
    {
      "data": "data:image/png;base64,...",
      "position": [0, 0]
    }
  ],
  "draw": []
}
```

## 测试策略

采用测试驱动实现：

1. 先增加 PNG 解码辅助函数和失败测试；
2. 验证画布仍为 52×16 RGB PNG；
3. 验证图标区域同时包含 `#FF2442`、白色和黑色像素；
4. 验证数字只出现在右侧区域并使用白色；
5. 验证 1–3 位、4–6 位和 7 位以上三类数值均完整落在边界内；
6. 验证 payload schema 与现有 MQTT 消费端兼容；
7. 运行项目完整 `npm run check`；
8. 生成本地预览图进行视觉检查；
9. 向 `10.10.20.181` 和 `10.10.20.123` 发布真实 XHS payload，由用户确认真机效果。

## 错误处理与兼容性

- 非数字、负数和空值按 `0` 显示。
- 渲染器不引入第三方运行时依赖。
- 不改变 Bridge HTTP API、MQTT 连接重试或 retained 行为。
- Ulanzi Studio 中 DIY 与 MQTT 的错误绑定属于设备/上位机行为，不在本次代码修改范围内；运行时必须保持相关 DIY 功能开启。

## 验收标准

- 预览图在 52×16 原始尺寸下可辨认出红色小红书图标和白色粉丝数。
- 当前粉丝数 `18` 使用大号两位数字显示。
- 参考图中的灰白状态点、昵称和下划线不出现。
- 完整测试、语法检查与发布检查全部通过。
- 两台在线 TC002 均能收到更新后的 `custom/display` payload。
